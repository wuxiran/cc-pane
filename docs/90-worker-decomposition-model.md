# 90 · 派工模型升级：契约冻结 + 所有权 manifest + leader 互感知（方向文档，未排期）

> 2026-08-09 三课题讨论的第三题产物（前两题见 docs/89 及其 §6 备注）。核心命题：一个大任务怎样
> 尽量多分 worker、加快速度。诊断结论：**现在分割弱，不是 worker 机制不够，而是分割发生在错误的
> 时刻、以错误的单位进行**——「一个 plan → 一个 worker」，plan 按功能切，功能内部是七步串行流水线，
> 可并行单位退化成「恰好互不相干的整功能」，机会天然稀少。

**状态**：方向文档，未排期。与 docs/74（task_binding 作为工作项骨干）、docs/89 §7（ctl/MCP 分界）互为衔接。

## 1. 两个原理性动作

### 1.1 先冻结契约，再放并行

功能内部串行的根因是接口在实现中才定型，下游等上游。改法：leader 先花一段**串行时间**把契约层写死并提交——Rust model 结构体、Tauri command 签名、TS 类型、事件契约表条目（`boundary_events.rs` 是现成范例）、测试骨架。契约冻结后，七步流水线的剩余六步从串行变扇形：Rust 侧 repo/service/command 一个 worker、TS 侧 service/store 一个、组件一个、测试一个，同时开工，在冻结的接口上会师。

**契约是并行的杠杆：串行写 200 行接口，换 2000 行实现的四路并行。** 这比任何调度机制都值钱。

### 1.2 识别任务的「宽深形状」，只对宽任务撒网

- **深任务**（一个精巧功能，设计决策层层级联）：串行内核压不掉，硬拆只产出接缝 bug。提速走**流水线化**：worker A 实现功能 1 的同时，leader 在 plan 功能 2、reviewer 在审功能 0——单功能仍串行，但 N 个 agent 满负荷。
- **宽任务**（几十个独立小项的集合）：bug backlog 清扫、migration 全仓 sweep、i18n 补齐、测试回填、docs/89 的工具收编（每个 CRUD 家族互相独立）——坚决撕碎，全量扇出。

「尽量多分 worker」的正确翻译：**建立识别宽任务的眼光，宽任务出现时坚决撕碎；深任务不拆实现、拆流水线。**

## 2. 三个机制缺口

### 2.1 派工单位缺「工作项 + 文件所有权 manifest」

leader 拆解时给每个 worker 一份 manifest：**独占写的文件集 + 只读的冻结契约文件 + 验收判据**。派发前 leader 校验各 manifest 文件集不相交，相交即拆错、回炉。效果：

- **不需要 worktree**（呼应第一题结论：所有权不相交的并行写，同一棵树就够了）；
- 冲突在**派发时刻被结构性排除**，不是事后靠 AI 解语义冲突（后者最贵且错了不报错）。

落点：docs/74 已把 task_binding 定位为工作项骨干，manifest 作为字段长在其上。

### 2.2 冷启动成本没有摊销

现状每个 worker 各自重读代码库，N 个 worker = N 倍探索 token。改法：leader 拆解时已理解全局，把「相关代码地图 + 契约位置 + 本项上下文」压成**简报**注入每个 worker 的 prompt。简报写一次、N 个 worker 复用，并行的 token 成本压掉大半——这直接回应「并行 = 烧 token」的质疑。

### 2.3 收尾是串行长尾（Amdahl 尾巴）

并行 30 分钟 + leader 集成测试 30 分钟 = 加速比腰斩。压法：

- worker 交付前自查**自己范围内**的编译（`cargo check -p xxx`、单文件 tsc），符合「worker 过程禁跑全量测试」的既有纪律；
- leader 只跑一轮全量门禁；
- 契约冻结在此二次收益：接缝错误少 → 集成期返工少。

## 3. leader 互感知：同工作空间的 AI 看板

> **⚠ 本节大部分机制已被 §6 终局裁决否决**——保留原文供后续翻案时参考，但实施以 §6 为准：
> 零新建（现成 `register_plan_leader` + memory 池 + skill 一步），claim/碰撞检查/交集判决在返工率数据证明前不建。

多 leader 并存的重复劳动问题。登记设施已有一半（`register_plan_leader`、`get_plan_collaboration`、`query_task_bindings`、workspace journal），缺的是**声明的内容、看板的动作、过期的回收**三样。

### 3.1 claim：注册时带范围声明

光登记「谁在干活」不够，要登记「干活的范围」：项目、认领的文件 globs/模块键、目标一句话。这是 §2.1 manifest 的向上聚合——**worker 的 manifest 聚合起来就是 leader 的 claim**。落点：plan 注册加 `scopeManifest` 字段，不新造表。

### 3.2 看板是 AI-first 的：pull 不 push，判决不原料

- **感知做成「开工先看板」的 pull**：planning skill 第 0 步固定查一次「本工作空间活跃 leader + 各自 claim」。不做 leader 互聊的 push——AI 间对话协商是 token 无底洞。
- **第一读者是 AI，人类视图只是派生渲染**：一条 claim = 一行稳定 schema 的记录（leaderId、sessionId、projectKey、scopeGlobs、goal、planRef、heartbeatAt），查询返回紧凑 JSON，不写 markdown 散文。
- **重叠判定由服务端算好**：scope 用可计算词汇（globs/模块键），后端做 glob 交集运算，响应直接带 `conflicts: [...]`。读板 leader 拿到的是判决不是原料——让模型对两段自然语言猜「是否重复」既贵又不可靠（「resume 链路」vs「恢复功能」对不上，globs 对得上），交集是确定性代码的活。
- **重叠的默认动作是呈给用户拍板**，不是 AI 自行谈判，更不是阻塞等待。**claim 是劝告性（advisory）不是硬锁**——硬锁的下场可预见：互等死锁，或死 leader 的锁卡住所有人。

### 3.3 板上不止 claim：「别重做」标记

重复劳动的大头不是重复写码，是**重复研究**（两个 leader 先后考古同一条链路，各烧一遍探索 token，比撞文件更常见更隐蔽）。板上/池里放三类可复用物：

- 调研简报（leader 完成调研后 `memory_add` 进 workspace 级 memory 池，下一个 leader 第 0 步 `memory_search` 先查）——§2.2 的摊销从「leader→自己的 workers」扩展到「leader→未来的 leaders」，全巧思里性价比最高的一件；
- 已做出的决策；
- 已验证过的死路。

### 3.4 回收必须设计时定死（本仓库血泪必修课）

「写入自动化、删除手动化」的单向流已坑过一次（worktree 项目记录积 14 条尸体，docs/62）。claim 只登记不回收，公告板三周后全是鬼影，感知机制反向变成噪音源。双保险：

- claim 绑定 leader 的 session id，**会话死则 claim 判死**（session 活性是现成信号）；
- **TTL 兜底**（如 24h 无心跳标 stale）。

另外 claim 落 workspace 级持久层，让 dev/release 隔离天然生效——别让 dev 实例的 claim 吓退 release 实例的 leader（串台 gotcha 的反向应用）。

## 4. 度量：防表演性并行

立两个数，没有它们「多分 worker」会滑向仪表盘热闹、实际比单 agent 串行还慢还贵：

- **墙钟加速比**：对比单 agent 干同样的活的 wall-clock；
- **返工率**：worker 产出被丢弃/重写的比例。

## 6. 终局裁决：设计承重，乐观默认

三轮攻防（碰撞触发惰性感知 → 「最后总能得出答案」反方论证 → 设计承重剃刀）后的结论，实施以本节为准。

### 6.1 反方论证成立的部分：「哪怕冲突，最后也能得出答案」

大上下文 AI 面对冲突永远能产出合并结果，但要分三笔账：

- **答案存在性 ≠ 正确性**：文本冲突（意图正交）合并近乎必对——多数情况；语义冲突（一方改了不变式，另一方基于旧不变式写）合并结果编译通过、看着合理、**错了不报错**——少数但最贵；意图冲突靠丢弃一方产出「得出答案」——付 2 倍拿 1 倍，即返工率。
- **验证成本是隐藏项**：语义合并后的 diff 要求审查者同时重建双方意图，是最贵的审查对象。vibecoding 的稀缺资源不是 AI 产出答案的能力，是验证带宽。
- **大上下文治不了上下文不对称**：合并者看得见两份 diff，看不见两个 worker 的推理过程；窗口解决「装得下」，不解决「不在场」。

### 6.2 剃刀：设计承重，为少数派不建常驻机制

**只要最初的设计不歪，实现层的冲突改就改了，跑得动就行。** 语义冲突之所以可怕，是因为它发生在不变式层面；而**契约冻结（§1.1）把不变式在派工前锁死、移出并行区**——之后 worker 间的碰撞全是浅层可合并的。用一段串行设计换全部并行自由，比任何碰撞检测都便宜且治本。

为少数派场景建常驻基础设施（claim 表、三级披露、服务端交集判决、写入 hook），等于每天向多数派收租：维护、心跳、状态漂移，光「回收」一项就是 docs/62 级别的坑源。**否决。**

### 6.3 存活清单

| 机制 | 裁决 | 理由 |
|---|---|---|
| 契约冻结（§1.1） | **保留，全案核心** | = 「设计不歪」的操作化 |
| 宽深形状判别（§1.2） | 保留 | 决定要不要并行的第一判断 |
| manifest（§2.1） | 降级为拆解模板 | 拆分时顺手写，帮助想清楚；不做强制校验/不相交检查 |
| 简报摊销（§2.2） | 保留 | 纯省 token，零机制 |
| 串行长尾压缩（§2.3） | 保留 | 纪律层，零机制 |
| worker 复述握手 | 保留 | 几乎零成本，误解第 1 分钟暴露 |
| leader 互感知（§3） | **收缩到零新建** | 现成 `register_plan_leader` + memory 池（简报/决策/死路），skill 加一步「先 list + 先搜」 |
| claim/碰撞检查/三级披露/交集判决 | **否决（数据前）** | §6.2 剃刀；返工率（§4）长期偏高再翻案 |
| 度量（§4） | 保留 | 乐观并发的代价表，翻案的唯一依据 |

### 6.4 AI 互理解的沉淀（协议层，非机制层）

即使机制否决，四条通信原则沉入 skill 文案（零基础设施）：**共享物优先于转述**（leader 验收看 diff 不看汇报）；**声明带证据指针**（命令+退出码、file:line、测试名，信任降为抽查）；**死路显式传递**（gotcha 的「症状→判定→解法」格式跨实例化，写进 memory 池）；**跨模型传规格、同模型可传意图**（给 Codex 的 plan 显式度高于给 Claude 的）。

## 7. skill 可执行的拆分规则（批次A 的落地文本）

背景：§1.2 的「宽深形状」与粒度经济学是给人读的；skill 里的 AI 需要**照着走就能走通的判定程序**——可枚举测试、硬阈值、切缝白名单，所有权衡在规则制定时做完，执行时只剩是非题。粒度模型来源：墙钟 ≈ 拆解 + max(单 worker) + **N × leader 验收**（验收随 N 线性涨的串行项决定最优 N 存在且不在极端）；**验收自动化程度是粒度的真正解锁器**——机器判定（测试+编译）则 N 可放大，leader 读 diff 则 N 必须小。

### Step 0 · 形状判定（按序问，命中即停）

1. 能列出 **≥6 个独立可交付项**，且「做完任一项不需要读另一项的产出」？→ **宽任务**，走 Step W。
2. 需要新增/修改跨 Rust-TS 边界的接口（command 签名、类型、事件契约）？→ **深任务**，走 Step D。
3. 还说不清要改哪些文件？→ **探索任务：禁止拆分**。单 agent 干，最多派只读子 agent 做研究。

### Step W · 宽任务聚簇

- 按「同族」聚簇（同一 CRUD 家族 / 同一目录 / 同一模式的重复项），**不按单项派工**。
- 簇大小硬阈值：单簇预估实现 **≥30 分钟**（不足则合并相邻簇）、**≤3 小时**（超则对半切）。
- N 上限看验收方式：验收 = 测试+编译（机器判）→ **N ≤ 8**；验收需 leader 读 diff → **N ≤ 3**。

### Step D · 深任务扇出

- **强制前置**：契约（模型结构体、command 签名、TS 类型、事件契约条目、测试骨架）先写完并**提交成 commit**；契约未提交，禁止派任何 worker。
- 切缝白名单四选：**Rust 侧 / TS service+store 侧 / 组件侧 / 测试侧**，即 N ≤ 4。不允许更细——深任务并行收益封顶于此，再细是 §6.2 剃刀否决的找事。
- 任一侧预估 <30 分钟 → 并入相邻侧，实际 N 缩小。

### Step G · 派发门（每个 worker 单元过三关，任一不过即回炉）

1. 验收判据能写成**一句可执行的话**（「X 测试过 + `cargo check -p Y` 过」）？写不出 = 缝切歪了，重切。
2. 该单元整个报废重做的损失 **≤3 小时**？超了 = 太粗，切开。
3. leader 验收此单元 **≤10 分钟**？超了 = 要么自动化验收，要么合并单元降 N。

### Step R · CLI 路由（每个过了 Step G 的单元，选执行者）

回应议题③的前半句「多终端适配」：CLI 差异不是适配问题，是**路由问题**——按单元性质选执行者，判定同样做成是非题：

1. **默认 Claude**。leader 通常是 Claude，同模型共享先验，通信成本最低（§6.4：同模型可传意图）。以下条件命中才改派。
2. **规格自足测试**：该单元的 manifest+简报+契约已写到「不需要知道本仓库怎么做事、照做即可」的程度？是 → 可派 Codex。否 → 两选一：补写到规格自足（然后可派），或留 Claude。**禁止把规格不自足的单元派给 Codex**——跨模型传意图是已知故障模式（§6.4）。
3. **机械簇优先外派**：宽任务（Step W）的簇若同时满足「规格自足 + 验收机器判」→ **Codex 优先**（省 Claude 配额，且机械重复对先验依赖最低）。
4. **评审必须异模型**：交叉评审/plan review 类只读单元 → 强制非 leader 同模型（现状即 Codex 审 Claude，专治「我审我」盲区）。这是唯一**强制**改派的类别。
5. **深任务的契约设计与集成收尾不外派**：这两段是全案语义密度最高处，leader（Claude）自己做。
6. **WSL 运行时守则**：派 WSL Codex 时带上已知 gotcha（prompt 未提交假死→发裸 CR 不 kill；原生 ELF 判定），见 CLAUDE.md 对应条目与工作空间 docs/61。
7. **opencode：暂不入路由**——无足够实测数据标定其边界；引入前先过 §7 尾注的标定夹具流程。

### Step X · 例外出口

走完流程算出 N=1 → 老实单 agent。**N=1 是合法且常见的答案，不是流程失败**。深任务序列的提速另走流水线错位（§1.2）：worker 实现功能 1 时，leader plan 功能 2、reviewer 审功能 0。

> 阈值（30min/3h/10min/N≤8/N≤3/≥6 项）是初始标定值，随 §4 两个度量（加速比、返工率）的实测数据修订。
>
> **版本漂移对策**：不同 AI 版本对规则沉默处的默认填充不同（规则没变、执行漂了）。三层对冲：①本节刻意选机械格式（是非题/硬阈值/白名单），对模型判断力依赖最小、跨版本最稳——叙事式指南（「灵活选择粒度」）是最不可移植的形态，禁用；②留 1~2 个标准样题当**标定夹具**，每换模型/CLI 大版本干跑一遍对照预期拆分（= prompt 的回归测试；这也是 fanout 采样唯一幸存的合法用途——换版本即能力边界重新变未知的时刻）；③§4 度量是版本无关的裁判，数字坏了直接修阈值，无需归因「新版本哪里理解不一样」。
