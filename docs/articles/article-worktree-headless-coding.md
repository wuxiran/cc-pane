# Headless Coding 时代，worktree 是不是伪需求？

> 基于 CC-Panes 项目一年多的多 agent 派工实践（docs/62、72、89、90 的实测记录）。
> 结论先行：**不是伪需求，但被严重过度处方了**——它是三个特例场景的专用工具，
> 不是并行编码的默认基础设施。我们自己就是从「默认给每个 worker 开 worktree」
> 一路退到「默认同树、特例才开」的。

## 一、worktree 为什么看起来是刚需

给每个 AI worker 一个独立 worktree，直觉上无懈可击：

- 文件系统级隔离，worker 之间物理上碰不到；
- 每个 worker 有自己的分支，产出天然成 PR；
- 主树干净，用户随时能在上面继续干活。

几乎所有 headless coding 编排方案（包括我们早期的 plantoworktree / fanout-compare
skill）都把它当默认项。逻辑是：并行写同一棵树 = 冲突，冲突 = 灾难，所以隔离。

这个推理链的问题出在第一环：**并行写同一棵树，并不必然冲突。**

## 二、账本另一面：worktree 的真实成本（全部实测）

隔离不是免费的。下面每一条都是本仓库踩过的真坑，不是理论推演。

### 1. 构建缓存的幻影错误

各 worktree 共享同一个 cargo target 目录（不共享则每个 worktree 独立编译全量依赖，
磁盘和时间都翻倍）。共享的代价：另一个 worktree 构建的 crate 会被本 worktree 复用，
报出**本地源码里根本不存在的编译错误**——实测报过 `missing field
expected_saved_session_id`，该字段只存在于另一个 worktree 的分支上。AI worker
遇到这种错误的默认动作是「改代码迎合报错」，等于让幻影污染真实代码。
增量缓存还会按构建会话堆积——实测积到 1164 个目录、176GB。

### 2. 元数据的单向流：写入自动化、删除手动化

编排系统会自动把 worktree 注册成项目（fanout 一次注册 N 个），但 `git worktree
remove` 不删注册记录，删记录的入口又不删磁盘。实测一个工作空间 21 条项目里
**14 条指向已删除目录**——主仓库淹没在 worktree 尸体里。这不是某处的 bug，
是「每开一个 worktree 就多一份要回收的状态」的结构性成本：分支、注册记录、
构建产物、`.env` 类不入库文件的拷贝，每样都要有人负责收尸，而自动化只长在写入端。

这条不是我们独有的毛病，是全行业通病，我们只是症状形态特殊（尸体多积了一层
应用侧元数据）。生态里有人实测积到 256 个 worktree、28GB 磁盘、700+ 条陈旧分支
（70% 指向几个月前已合并的分支）；Claude Code 官方仓库挂着一串同病 issue
（#26725「stale worktrees are never cleaned up」、#45645 残留 git config 弄坏
其他 IDE 工具），直到 v2.1.76 才补上中断后的自动清理；甚至催生了 worktrunk、
workz 这类专职收尸工具——它们的存在本身就是通病的证明。批评文
《Every AI Agent Tool Creates Git Worktrees. None of Them Make Worktrees
Actually Work》总结得准：每个工具都假设回收和环境是别人的事。

### 3. 归属关系是个坑洞密布的派生问题

`git worktree list` 从任何一个 worktree 跑都返回同一份全量列表——拿它做父子关系
会互认成环；monorepo 子目录项目会被误认成假 worktree。我们最终花了一整个批次
（docs/62）才把「侧边栏 21 条平铺」修成正确的分组树。这些工程量全部由
「默认开 worktree」的策略诱发。

### 4. 合并期是 Amdahl 尾巴，worktree 只是推迟冲突而非消灭冲突

这是最核心的一条。worktree 把冲突从「写入时」推迟到「合并时」，但语义冲突
（一方改了不变式，另一方基于旧不变式写码）**在合并时更贵**：合并结果编译通过、
看着合理、错了不报错；审查者要同时重建双方意图，是最贵的审查对象。
headless coding 的稀缺资源不是 AI 产出答案的能力，是**人的验证带宽**——
worktree 在这条最贵的账上一分钱都省不下来。

## 三、真正消灭冲突的是派工设计，不是文件系统

我们现在的派工模型（docs/90，三轮攻防后的终局裁决）建立在两个动作上：

**契约冻结先行。** leader 先花一段串行时间把接口层写死并提交——数据模型、
命令签名、类型定义、事件契约、测试骨架。不变式在派工前锁死、移出并行区之后，
worker 间残余的碰撞全是浅层文本级、近乎必对的合并。串行写 200 行接口，
换 2000 行实现的四路并行——这比任何隔离机制都值钱。

**所有权 manifest。** 拆解时给每个 worker 一份清单：独占写的文件集 + 只读的
契约文件。派发前校验各文件集不相交，相交即拆错、回炉。冲突在**派发时刻被
结构性排除**，而不是事后靠 AI 解语义冲突。

做到这两条，结论自然浮出来：**所有权不相交的并行写，同一棵树就够了。**
worker A 写 Rust 侧、worker B 写 TS store、worker C 写组件、worker D 写测试，
四个进程同时在一棵树上跑，git status 里的改动互不重叠，合并这一步干脆消失了。

反过来说：如果你的拆分做不到所有权不相交，worktree 也救不了你——它只是把
今天的写冲突换成明天的合并冲突，且把最难的语义冲突留到最贵的时刻爆炸。

## 四、幸存的三个场景：worktree 真正的处方范围

把默认项砍掉之后，worktree 在我们的实践里剩下三个不可替代的场景：

1. **同题多解（fanout-compare）**。同一个 plan 派给 N 个 worker 各写一份实现，
   完赛后对比挑赢家。N 份实现改的是**同一批文件**，所有权天然全交，这是唯一
   「结构上不可能同树」的场景。（即便如此，我们也把 fanout 降级成了能力边界
   标定工具——日常多视角需求收敛到「一份实现 + 一次异模型交叉评审」，更便宜。）

2. **并行中途要跑 build / test**。构建和测试读的是整棵树的一致快照。同树并行时
   worker A 跑 `cargo test`，worker B 正好写了半个函数，测试挂掉且归因困难。
   需要在并行**过程中**反复起门禁的任务，值得为跑测试的那个 worker 开 worktree。

3. **保住主树**。用户自己正在主树上改东西（未提交的 dirty 状态），此时派出的
   worker 无论所有权多干净都不该碰主树——人的工作现场优先级高于一切编排便利。

三条共性：**都是「同一批文件确实会被多方触碰」的场景**。worktree 的正确定位
是这类场景的专用工具，处方开出去之前先问一句：所有权真的交叠吗？

## 五、为什么 headless 语境下这个结论更成立

worktree 的原始需求方是**人**：人切分支有心智成本（stash、上下文重建、IDE 索引
重刷），多份物理目录是对人脑单线程的补偿。而 headless 编排里：

- worker 的「工作现场」是 prompt + manifest，不是 shell 的 cwd 状态——它不需要
  一个属于自己的目录来记住自己在干什么；
- 冲突可以在**派发时刻**被 leader 结构性排除，人类协作做不到这一点（你没法给
  同事发 manifest 并校验不相交），所以人类需要隔离兜底，AI 编排不需要；
- AI 的产出要过人的验证带宽这个总闸，隔离做得越彻底、分支开得越多，合并审查
  的账单越长——隔离成本从「写入方付」转嫁成「验证方付」，恰好付在最贵处。

所以答案是：**worktree 不是伪需求，「默认 worktree」才是。** 它是从人类协作
习惯里无脑继承过来的默认值，在 headless coding 的成本结构下需要重新开处方——
默认同树 + 契约冻结 + 所有权不相交，三个特例场景才掏出 worktree。

## 附：一条可操作的判定顺序

派工前按序问，命中即停：

1. 是同题多解对比？→ worktree（每份实现一个）。
2. worker 并行期间需要反复跑全量 build/test？→ 给跑门禁的 worker 开 worktree。
3. 主树上有用户未提交的工作？→ worker 全体去 worktree。
4. 以上都不是 → 冻结契约、切 manifest、校验不相交，**同一棵树，直接开工**。
   拆不出不相交的 manifest？那不是该开 worktree，是该回炉重拆——或者承认
   这是个深任务，老实串行（N=1 是合法且常见的答案，不是流程失败）。
