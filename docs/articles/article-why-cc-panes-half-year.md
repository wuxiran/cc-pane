# 从「让两个终端互相看见」到 19 个 agent：CC-Panes 的半年

> 2026-02-16 立项，到今天刚好半年。这篇不讲功能列表，讲六个决定项目走向的时刻——
> 每一个都有提交号或实测数据，你可以自己去仓库里核。

## 一、生日那天开工

2026 年 2 月 16 日，我的生日，我提交了 CC-Panes 的第一行代码（`e342812`，那时 `package.json` 里写着 `0.1.0`）。

选这一天没什么玄学理由，就是想让这件事有个记得住的起点。

做它的动机也不复杂：**旧编辑器不是不够好，是它服务的那个人已经不在了。** IDE 的每一寸界面都在优化「人怎么更快地敲代码」——光标、补全、跳转定义、单文件聚焦，这些它做得非常好。但现在敲代码的不是人，人在派工和验收。这两件事，IDE 里连概念都没有。

AI 是新的生产工具，而 IDE 是旧生产关系的固化形态——它把「一个人、一个光标、一个文件」焊死在了界面里。工具变了，组织方式就得跟着变。

## 二、如果每个终端能看到其他终端的对话，那不是很酷吗？

基础终端很快就写好了。真正让这个项目变成「不是编辑器」的，是 3 月 10 日那个提交。

`dcbb16a` — v0.4.0，Orchestrator MCP 服务。axum HTTP 服务 + MCP Server、任务启动与状态查询 API、前端事件监听。**从那一刻起，一个终端里的 AI 可以读到另一个终端的对话。**

第二天，`24fb78d`：「PTY 编程输入修复 — `submit_to_session` 端点 + prompt 注入时序拆分」。光能读不够，还要能写进去、能按回车。提交名里那个「时序拆分」是被现实教育的结果——填内容和提交必须分成两步。

然后我撞上了这个项目的第一个坑：**回车在 Windows 上必须发 `\r`，不能发 `\n`**。PowerShell 只认 CR。这条至今还是 CLAUDE.md 里 61 条踩坑记录的第一条。

距立项第 23 天。那时候市面上还没人把「让 agent 互相看见彼此的对话」当成一个功能。

## 三、工作空间：借鉴符号链接，但没用符号链接

我借鉴了 VS Code 和 IntelliJ 的工作空间概念——我认为工作空间是最适合 vibecoding 的形式。

先说个人尽皆知的痛点：Claude 和 Codex 都喜欢在项目文件夹里塞 `.claude`、`.codex`。项目做到一半，你的 GitHub 仓库里全是这些点目录。而且它们混了两种生命周期完全不同的东西：`skills`、`agents`、`commands` 是团队资产，该入库；`settings.local.json`、`plans/`、`worktrees/` 是个人运行时垃圾，该忽略。CLI 厂商把这两类塞进了同一个地方。

工作空间的思路我借鉴的是 Linux 文件链接——**引用，而不是复制**。项目不搬家，工作空间只存一行指向它的路径。但落地时我没用 symlink，用的是一张 CSV 清单：

```csv
path,alias,branch,status
D:\01_workspace_ai\erp-workspace\yunzhu-ui-admin-vben,ERP 前端,erp,dirty
D:\01_workspace_ai\erp-workspace\yunzhu-erp,ERP 后端,feature/erp,dirty
```

为什么不用真链接，三个理由：

- **跨平台**。Windows 上建 symlink 要提权，跨 WSL / UNC 边界还会碎。而这张表里 `D:\...` 和 `/mnt/d/...` 两种路径形态可以混着存——文件系统链接做不到。
- **能带元数据**。链接只能表达「指向哪」；清单能顺带带上别名、分支、脏净状态。侧边栏里那些分支名和改动标记就是从这儿来的。
- **零侵入**。加入工作空间不在你的仓库里留任何痕迹，归属关系完全活在工作空间侧。

需要说清楚的是：**工作空间并不消灭 `.claude` 污染**，那个还得靠 `.gitignore` 分类处置（skill 入库、运行时忽略）。工作空间解决的是另一个问题——一堆散落各处的仓库，怎么被当成一件事来管。

## 四、spec：从架构降级成功能

立项当天我还引进了 spec——当时最火的多 agent 协作方案（`f45a5c6`）。给项目建一棵规范树：前端怎么写、后端怎么写、跨层怎么想，落成 21 个文档；再用一个 391 行的 hook 在每个子 agent 启动时把这份 spec 注入进去。**让所有 agent 读同一份规范。**

用了一个半月。4 月 4 日，`9524c8c`，我把整棵规范树删了。

直接原因很朴素：**规范是吃上下文的。** 而且吃法很难看——每个 agent、每次会话都要读一遍，成本按 agent 数乘会话数线性涨，可其中绝大部分内容跟这次要干的事没关系。我付的是常驻费用，买到的是弥散收益。

更根本的问题是：**规范在一人公司、在个人项目里，真的有那么重要吗？** 我认为没有。规范的价值在于让一群互不了解的人写出风格一致的代码——它治的是人的协作摩擦。而这里没有那群人，只有我和一堆 agent。功能先产出，不满意后面烧 token 改，完全来得及。

但这不等于「什么都不用先想清楚」。删掉规范树之后，我反而更看重一样东西——**契约**。区别在于：规范是「永远为真的知识」，契约是「这一次要做什么」。前者常驻、弥散、大部分时候用不上；后者一次性、集中，每一条都直接决定这次会不会返工。

**上下文不该花在永远为真的知识上，该花在这一次要做什么上。** 这句话是后来所有编排设计的地基。

「先产出、后迭代」也有边界：能被测试和编译抓住的错，事后改确实便宜；改不动的是**不变式层面的错**——一方改了不变式、另一方基于旧不变式写码，合并结果编译通过、看着合理、错了不报错。所以契约只锁接口和不变式这一层（一两百行），其余全部交给先产出后迭代。这也是为什么我要的是一份 plan，而不是 21 个规范文件。

spec 本身没被扔掉，它降级成了一个普通功能，今天还在 CC-Panes 里跑（`spec_service.rs`，管 Spec 与 Todo 的双向绑定）。它只是不再是编排的骨架了。**同一个东西从架构降级成功能，这也是一种进步。**

## 五、额度不够，逼出了第一个编排 skill

删掉规范树三天后，`/plantocodex` 诞生了。

起因很不体面：Claude Code 那边出了点状况，我每天的额度得优先留给客户用，只能被迫改用 Codex 5.4。

5.4 是真的不说人话。你跟它讲一个意图，它这里拿一刀、那里砍一刀，回来给你一个能编译但不是你要的东西。同样一句话给 Claude，它会顺着你的思路往下想；给 Codex，它只顺着字面执行。

想了很久我才明白，这不是它笨——是**我给错了输入**。同模型之间可以传意图，因为它跟你共享一套先验；跨模型只能传规格。我一直在用「跟 Claude 说话」的方式跟 Codex 说话。

于是有了 `/plantocodex`（2026-04-07，`73617cf`，距开工第 51 天）：Claude 不写代码，只负责把事情想清楚——写成一份显式到不需要任何背景知识就能照做的 plan；Codex 不做判断，只负责按 plan 实现。两个模型各干自己擅长的那件事，**中间那份 plan 就是它们之间的契约。**

讽刺的是，后来额度恢复了，我也不想回去了。让一个实例专心想、另一个专心写，比一个实例边想边写更快、返工更少。**约束逼出来的东西，往往比主动设计的更好。**

那一个 skill，到 7 月底长成了六个：`plan2codexwsl`（5-17）、`plantocc` 与 `planreview`（7-04）、`fanout-compare` 与 `plantoworktree`（7-25）。

## 六、于是不需要的东西，比需要的东西更说明问题

契约冻结这一条立住之后，很多当时看着必需的东西，反而变成了不必需。

**共享黑板不需要了。** 那段时间流行让 agent 共读共写一块共享状态，谁做到哪一步写在上面，别人自己去看；改同一个文件就上锁排队。听起来很像真实团队。但共享状态治的是「冲突发生后怎么办」，契约治的是「冲突根本不发生」——把不变式在派工前锁死、移出并行区，之后 worker 之间残余的碰撞全是浅层、文本级、合并近乎必对的。而黑板上的信息要维护、要心跳、要回收，三周后全是鬼影，感知机制反过来变成噪音源；契约写完就提交进 git，它不会腐烂。

**默认 worktree 也不需要了。** 所有权不相交的并行写，同一棵树就够了。worktree 只把冲突从写入时推迟到合并时，而语义冲突在合并时更贵——编译通过、看着合理、错了不报错，审查者要同时重建双方意图。这是最贵的审查对象。我们从「默认给每个 worker 开 worktree」一路退到「默认同树、三个特例才开」（同题多解、并行期跑 build/test、主树上有用户未提交的活）。

一句话总结这半年学到的最重要的事：**headless coding 的稀缺资源不是 AI 产出答案的能力，是人的验证带宽。** 所有省不下验证带宽的机制，都是花架子。

## 七、现在

写这篇的时候，我这台机器上：

- **19 个 Claude 会话**同时在线，分布在 9 个布局、17 个分屏面板、33 个标签页里，横跨 7 个项目
- 近 30 天在 **36 个不同仓库**、80 个工作目录上派过活（678 次 agent 启动）
- CC-Panes 全家桶（主进程 + daemon + web + 27 个 WebView2 进程）占 **1.9 GB**；19 个 agent 自己占 **7.1 GB**——**编排壳只占 21%**

对照一下 IDE 的模型：一个窗口一个项目。JetBrains 系单窗口 2–4GB，今天这 7 个项目就是 20GB 以上，这个月那 80 个工作目录是 160GB 以上。我这台机器 94GB，装不下一半——**不是慢，是物理上做不到**。

**过去一个人能同时推进几个项目，取决于你能开几个 IDE 窗口，也就是取决于内存，上限是两三个。现在它取决于你能验收多少 agent 的产出。**

半年的账：**971 次提交**（squash-merge 工作流，每次压着一整条 PR）、**103 个活跃开发日**、**345,891 行源码**、**88 个版本**（平均不到两天一个）、**7842 次安装包下载**（其中 89% 是 Windows），以及 **61 条踩坑记录**——26 条是 Windows/WSL 专属的，别的工具连遇到的机会都没有。

第一条还是那个：回车得发 `\r`。
